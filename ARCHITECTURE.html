二、目标架构（三层）

不管以后加多少功能，都按这三层来组织，互不干扰：

┌─────────────────────────────────────────────────────┐ │ 第三层：界面层（UI Pages） │ │ index.html · map-measure · hydraulics · ai-chat │ │ quote.html · report.html · settings.html │ │ 每个页面独立，通过 runye-nav 导航，通过 localStorage 传数据 │ ├─────────────────────────────────────────────────────┤ │ 第二层：业务服务层（Services） │ │ ryHydraulic · ryMap · ryQuote · ryReport · ryAI │ │ 每个服务是一个 JS 对象，页面调它，它不关心页面长什么样 │ ├─────────────────────────────────────────────────────┤ │ 第一层：计算引擎层（Core Engine） │ │ hc-core（水力公式）· design-core（设计） │ │ hydraulics-core（管网递推）· epanet-wasm（对照） │ │ 纯计算，输入参数→输出结果，不碰DOM，不碰页面 │ └─────────────────────────────────────────────────────┘

分层原则

  1. 引擎层不碰页面：hc-core.js 和 hydraulics-core.js 只做数学，输入参数输出数字，不操作DOM
  2. 服务层不碰样式：ryQuote 算材料清单时只返回数据，不写HTML
  3. 页面层不写公式：页面只负责收集用户输入、调服务、显示结果。所有计算逻辑往下沉到服务层和引擎层

四、后续功能怎么接入

以后加新功能，按这个套路走：

新增一个"材料报价"功能

  1. 引擎层：如果需要计算（比如管材单价×长度），写到 hydraulic-calc/quote-core.js
  2. 服务层：新建 ry-quote.js，提供 RyQuote.generate(segRows, tapeRows) 返回报价数据
  3. 页面层：AI对话里说"出报价"→ 调 RyQuote.generate() → 结果卡片显示在右侧
  4. 导航：在 runye-nav.js 加一个菜单项

新增一个功能时的文件命名规则

类型命名规则例子
新页面runye-功能名.htmlrunye-quote.html
新计算模块功能名-core.js 放 hydraulic-calc/hydraulic-calc/quote-core.js
新服务runye-功能名.js 放根目录runye-quote.js
新样式优先复用 runye-theme.css，不另开—

六、发展路线建议

近期（1-2个月）：把现有功能串起来

  1. AI对话页接真实计算：现在是假数据，把 runye-hydraulics-core.js 接进去，说"算一下"真出结果
  2. 材料报价模块：管段长度×管径单价，自动出清单和总价
  3. 清理临时文件：根目录的 _v*_pre.html、verify_*.js、_tmp_*.html 统一移到 _archive/
  4. 导航栏更新：加AI助手入口，按使用频率排序

中期（3-6个月）：做深专业能力

  1. 全毛管批量模拟：现在只算最差一条，以后每条毛管都算DU，出全图均匀度
  2. 轮灌组设计：自动分轮灌组，算每组同时工作的支管数，优化水泵选型
  3. 冲洗工况校核：滴灌带定期冲洗时的流量和压力校核
  4. 地形坡度修正：接入DEM高程数据，不是手填坡度
  5. 导出PDF设计报告：把校核结果+材料清单+图纸打包成一份给客户的报告

远期（6个月+）：产品化

  1. 接大模型API：AI对话从规则匹配升级到真·自然语言理解
  2. 多项目管理：现在只有一个项目，以后要能存多个地块、切换
  3. 客户分享链接：生成一个链接发给种植户看结果，不用装软件
  4. 手机端适配：现场踏勘时手机上就能看管网和参数
  5. 云同步：现在是localStorage存在本地，以后加个简单后端同步项目

七、一个重要的建议：不要急着换框架

你现在是纯HTML+JS，没有React、没有构建工具。这个状态其实很好——双击文件就能跑，不需要Node.js环境，不需要打包。

等代码量超过50个JS文件、或者多人协作的时候，再考虑：

  • 打包工具：Vite（最简单，10分钟上手）
  • 框架：暂时不需要，原生JS够用
  • 后端：等需要多项目同步时再加，用什么都行

epanet-js用Next.js是因为它有团队、要登录、要云函数。你现在一个人、纯本地用，不需要这些复杂度。
