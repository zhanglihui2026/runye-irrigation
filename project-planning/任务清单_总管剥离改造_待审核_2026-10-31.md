## 1. 背景与已定决策

### 1.1 产品结论（已拍板）

- 总管是**全局管线**，不属于任何分区内部管网。
- 总管改由用户在【在线地图页】在地图/卫星底图上**手绘**，贴合田埂、道路、水源实景。
- **分区与管路页取消自动生成总管**，各分区改由**三通独立接驳**。
- 系统**不**自动生成总管；当前版本**不**使用 AI 优化总管走向。

### 1.2 页面架构（固定，不新增页面）

| 页面 | 职责 |
| --- | --- |
| A `#onlineMapSection` | 地块绘制、**总管手绘**、水力复核 |
| B `#pipePlanSection` | 自动分区、生成分区内主管/支管/滴灌带 |

### 1.3 数据流

```
改造前： A 画地块 ─→ B 自动分区 ─→ B 生成内部管网 ─→ B 自己凑一条总管(frontPipe)
                                                        └→ 出图/材料/水力/DXF

改造后： A 画地块 ─→ B 自动分区 ─→ B 生成内部管网（不再产出总管）
          A 手绘总管 ──┐
          B 回传管网 ──┴→ A 叠加只读显示 + 水力复核（总管长度/流量由 A 的几何提供）
```

关键约束：**B 页不许再产出总管几何**，但**可以把 A 页的总管当只读底图显示**。

## 2. 现状事实（请复核，每条附复核命令）

> 标记：✅＝我本轮亲自跑过/读过；⚠️＝沿用 v1 结论，建议复核者再确认一次。

### 2.1 ✅ 事实一：`frontPipe` 是**一名两义**

最容易导致误删的一条。

| | 形态 | 含义 | 出现位置 | 处置 |
| --- | --- | --- | --- | --- |
| ① **几何折线** | `data.frontPipe=[{x,y},…]` | 总管地面走向点列（米） | `tlDiagramData` → 渲染/签名/DXF | **取消自动生成** |
| ② **水力选型结果** | `r.frontPipe={od,id,v}` | 联合流量算出的总管管径/流速 | `computeThreeLevel()` 返回值 | **原样保留** |

判据：带 `.od/.id/.v` 是 ②；带 `.length` / `[0].x` 是 ①。

```bash
grep -n "frontPipe" mod/inline-09.js | head -60
```

### 2.2 ✅ 事实二：「自动生成」实际只有一处兜底

`mod/inline-09.js:4152-4160`——当已有折线退化成一点（长度 < 0.5m）时，贴地块边线补一条：

```js
if (frontPipe && Math.hypot(frontPipe[1].x-frontPipe[0].x, frontPipe[1].y-frontPipe[0].y) < 0.5) {
  frontPipe = [{x:tlGeoBounds.minX, y:tlfFbY}, {x:tlGeoBounds.minX + tlGeoBounds.w, y:tlfFbY}];  // 贴边横线
  frontPipe = [{x:tlfFbX, y:tlGeoBounds.minY}, {x:tlfFbX, y:tlGeoBounds.minY + tlGeoBounds.h}];  // 贴边竖线
}
```

加上 `4098 / 4111 / 4130` 三个走向分支入口。**这就是全部**。

```bash
sed -n '4150,4165p' mod/inline-09.js
```

### 2.3 ✅ 事实三：有 7 处取索引/长度**没有判空**

`frontPipe` 一旦为 `null`，这些位置会抛 `TypeError`：

| 行 | 代码形态 |
| --- | --- |
| `4196` | `if (frontPipe.length > 2)` |
| `4220` | `var sfa=frontPipe[0], sfb=frontPipe[frontPipe.length-1]` |
| `4231` | `var scEnd=frontPipe[0]` |
| `4246` | `var fEnd=frontPipe[frontPipe.length-1]` |
| `4250` | `Math.min(frontPipe[0].x, fEnd.x)` |
| `4287` | `var tlfFy=frontPipe[0].y` |
| `4295` | `var tlfFx=frontPipe[0].x` |

对比 `4182`、`4245` 的 `if(frontPipe){` 已有守卫 —— 作者知道要判空，只是漏了这几处。

```bash
sed -n '4190,4200p;4215,4260p;4285,4300p' mod/inline-09.js
```

### 2.4 ✅ 事实四：第 `1003` 行会「整图放弃」

```js
if (!d || !d.frontPipe || d.frontPipe.length < 2 || !d.mainPipes || !d.mainPipes.length) return EMPTY;
```

`frontPipe` 为空时**不是少画一条线，而是整张图不生成**。拆生成必须同步放宽，
否则症状是「点生成管线图完全没反应」，极难排查。

```bash
sed -n '1000,1010p' mod/inline-09.js
```

### 2.5 ✅ 事实五（v2 新增）：规范模型会**整体替换** `network` —— 新字段放错位置会被静默抹掉

这是 v2 最重要的补充。三个环环相扣的机制：

1. **`network` 是白名单式序列化。**
   `core/drawing-design-legacy-adapter.js:62-78` 只映射这 8 个键：
   `mainPipes / branchPipes / subBranchPipes / source / valves / ids / hidden / nextPipeId`。
   反向 `toLegacyPatch`（`:160-177`）同样只吐这 8 个。
   ⇒ 你在 runtime 里塞一个 `network.trunk`，**过一趟适配器就没了**。

2. **L2 提交是整体覆盖。**
   `mod/inline-12.js:140-146`：
   ```js
   model.updatePlot(design, plotId, design.revision, function(target){
     target.geometry.boundary = …; target.partition = …; target.network = …;  // ← 整块替换
   });
   ```
   ⇒ 只要 `network` 参与覆盖，而某个适配器没映射新字段，**用户每次拖分区线/画管网，总管几何就被清空一次**，
   且不报错（见 §10 的"静默回滚"）。

3. **CAS 比对整块 `network`。**
   `mod/inline-12.js:130-138` 的 `comparable()` 把 `{boundary, partition, network}` 整体
   `JSON.stringify` 后比对。新字段进 `network` 就意味着**它也进了 CAS 比对**：
   A 页改总管 ⇒ 与 B 页持有的 runtime 状态不一致 ⇒ B 页下一次提交被判"对账失败"，
   `ppCommitSinglePlotEdit` 返回 `false` ⇒ `ppApplySlot(preimage)` 静默回滚，只有 console 一行 warn。

**结论**：总管几何**不建议**塞进 `network`。§5 给了三个落位方案与推荐。

```bash
sed -n '130,150p' mod/inline-12.js
sed -n '58,80p;158,180p' core/drawing-design-legacy-adapter.js
sed -n '36,50p' core/drawing-design-model.js      # validateNetwork 只查必需键，不拒多余键
```

## 8. 开放问题（请拍板，每项附施工代价）

**Q1 · 旧存档里已有的 `frontPipe` 几何怎么办？**
A. 忽略（读入即丢弃，代价：0）／B. 显示为灰色参考底网不可编辑（+80 行）／C. 首次打开提示"迁移为手绘总管"（+150 行，且要处理迁移后用户不满意再撤销）

**Q2 · 材料表「总管」那一行归谁？**
A. 移出 B 页材料表，只在 A 页统计（**推荐**，口径最干净，+20 行）／B. 保留行但读 A 页数据（+10 行，但两页数字要保证一致）／C. 变成"待手绘"占位（用户可能误读为 0 米）

**Q3 · 水源点 `sourcePos` 跟谁走？**
现在由 `frontPipe` 端点自动定位（`inline-09.js:4231-4234` 找最近端点）。取消后水源只能由用户在 A 页标记，那 B 页的「水源到首区距离」`planSrcDist` 怎么算？
选项：① 取总管起点到最近分区边界（+40 行）／② 直接不计该段（水力结果偏差）／③ 由用户在 A 页显式指定"供水点"（+60 行）

**Q4 · 坐标系统一方案？**
地图经纬度 → 米制的投影参数（原点 / 椭球 / 是否 `cosLat` 近似）必须 A/B 两页一致。
**建议写死一组常量并加断言校验**（而不是各模块各算一次）。代价 +30 行，能省掉最难查的一类 bug。

**Q5 · `tl_frontPipeLen`（总管长度输入框）保留吗？**
保留＝没画总管时可兜底估算（体验顺但口径松）；不保留＝强制先画总管才能生成（口径严但会挡住老用户）。

**Q6 · 三通接驳的拓扑怎么定义？**
"各分区由三通独立接驳"：每个分区一个三通？还是允许一个三通供多个分区？水力拆分流量按什么规则？
**这条不定，T6.6 与水力模型都无法开工**，是全表最优先的待拍板项。

**Q7 · 多干线 + 「水源唯一」的矛盾**
需求写"整个方案唯一水源识别点"，但支持多段独立干线。多干线时是否每条都必须接水源？

**Q8（v2 新增）· 总管是「每块地一条」还是「整个方案一条」？**
决定 §5 走方案 B 还是 C。选 C 的代价是新增项目级事务域（+200 行且要重做回归）。

**Q9（v2 新增）· 总管绘制是否要参与「规范模型」的撤销/重做统一样式？**
现有 L2/L3 各有自己的撤销语义，若总管另开一套，用户按 `Ctrl+Z` 时会有三种不同范围。

**Q10（v2 新增，与 Q8 合并考虑）· T2 是否保留"自动生成"开关？**
保留＝可一键退回旧行为（推荐，+15 行）；不保留＝彻底干净但首发风险高。
