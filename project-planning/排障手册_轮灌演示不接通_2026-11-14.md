# 排障手册：轮灌演示「明明接上了却报没接通」

> 适用：点「演示轮灌」不出水、提示「总管与主管没接通」、或提示「N 区支管两端都没进入水路」。
> 首次成文 2026-11-14，起因是一次拖了 6 个版本、3 次回滚才定位的连续报障。
> 代码入口：`mod/map-flow-demo.js`（唯一的演示引擎，约 1700 行）。
>
> 同目录另有两份相关文档，**不要互相抄**：
> - 《轮灌动画节点已连接仍拒播故障记录_2026-11-14》= 本次故障的事实卷宗（改了什么、风险在哪、后续要防什么）；
> - 《轮灌演示数据与水路一致性审计_2026-11-10》= 数据链路审计。
> 本文只回答一件事：**下次再出现，按什么顺序查。**

## 1. 三分钟定位（按顺序做）

### 第 1 步：进「在线地图」→ F12 → Console → 粘贴

```js
RyMapFlowDemo.whyNotText(0)     // 第 1 组；换 1、2、3 看别的轮灌组
```

输出形如：

```
【演示诊断】门禁=validation / code=node-not-connected；主管 3 / 支管 12 / 阀门 12 / 配件 0 / 总管段 1 / 分区 12 / 轮灌组 4；...
 【数据】主管3/支管12/阀门12/配件0/总管段1（共12区）；总管接上节点 0/3；最近节点离主管 0.96m、离总管 0.96m（严格容差 0.5 / 1.5）；成路 24 条/目标 24/馈线 0。
```

**只看三样：门禁、code、最近节点离主管/离总管的米数。** 剩下的是给对账用的。

### 第 2 步：查表

| 门禁 `gate` | `code` | 含义 | 下一步查什么 |
|---|---|---|---|
| `collect` | — | 简图数据没进来 | `whyNot().counts` 是否全 0；在线地图是否加载了已发布管网快照；`window.tlDiagramData` 是否存在 |
| `validation` | `no-trunk` | 没有手绘总管 | 地图上画总管（要吸到驳接点） |
| `validation` | `no-data` | 图上没有分区主管 | 回「分区与管路」生成施工图 |
| `validation` | `no-node` | 快照里没有主管施工节点 | 在主管上放节点并重新生成施工图 |
| `validation` | `node-not-connected` | **总管在，节点也在，但判定没碰到** | ★ 看【数据】里「最近节点离主管 x m」。x ≤ 3 却报错 = 程序问题；x 明显 > 3 = 真的没画到 |
| `validation` | `partial` | 部分轮灌组不通 | `brokenGroups` / `brokenMains`，先修点名的那几组 |
| `routes` | — | 校验过了，图建不出来或覆盖不全 | 看 `coverage.wholeFieldClosed`、`coverage.missingZones`、`diag.zones[].reason` |
| `pass` | — | 能演示 | 若界面仍不出水，问题不在演示引擎，去查图层/动画（`FLOW_PANE='ryMapFlowPane'`） |

### 第 3 步：看原始诊断（比文案细）

```js
RyMapFlowDemo.lastDiagnostics()
```

字段：`{blocked, active, missing, zones:[{zi,reason}], fittings:{placed,dup,offLine,noPipe}, couplers, couplersLoose, nodeTotal, nodeProbe:{minMainD,minTrunkD}, graphNodes, rootDeg, targetsInGraph, debug}`

- `couplers / nodeTotal` → 总管实际接上几个节点。**0/3 就是本案**。
- `nodeProbe.minMainD` → 最近节点到「自己那根主管」的垂距（米）。
- `nodeProbe.minTrunkD` → 最近节点到「总管」的垂距（米）。
- `graphNodes / rootDeg` → 图里节点数、根（水源）的度数。`rootDeg=0` = 根是孤岛。
- `zones[].reason` → 逐区人话原因。

## 2. 两个真实根因（2026-11 这两次）

### 根因① 快照里两个字段跨了「世界」，差半个显示间距 ≈ 0.96 m

v1082 把地图拆成**双世界**：

| | 存什么 | 用在哪 |
|---|---|---|
| 实体世界 `mains/branches` | 真实中心线 | 水力计算、寻路、连接判定 |
| 显示世界 `displayMains/displayBranches` | 整条线刚性平移 ±gap/2 | 渲染、点击命中（主支管要分得开） |

规则写在 `mod/online-map.js` 的 `RyMapPointProjector` 注释里：**可见/可点 → 显示世界；存储/寻路 → 实体世界；两界只经这一层换算。**

演示引擎 `collect()` 直接读发布快照的原始 ll：

```js
routeGeometry.mains      → mainsLL          （实体）
routeGeometry.displayMains → displayMainsLL  （显示副本）
routeGeometry.nodes[].ll → nodesLL          （节点的落点）
```

问题就在这里：**节点的落点坐标天然比实体中心线偏约 0.96 m**（= 半个显示间距，随管线间距而变；用户当年实测「阀离支管 0.96m」就是同一个数）。而 coupler 的判定是：

```js
if (mp.d <= LINK_EPS_M) { ... }   // LINK_EPS_M = 0.5
```

`0.96 > 0.5` ⇒ 三个接口**全部静默 return** ⇒ 一个 coupler 都没建 ⇒ 水源根节点在图上孤立 ⇒ 全图不可达 ⇒ 12 个区全报「支管两端都没进入水路」。

**修复（v1084d）**：模块常量 `LOOSE_ATTACH_M = 3.0` 做宽松兜底——严格（0.5 / 1.5）优先，不中时 3 m 内仍认接通，并写进 `couplersLoose` 记账，提示里明说「其中 N 个为宽松吸附」。为什么 3 m 安全：地块尺度几十米、相邻主管相距 30 m 以上，3 m 不会错连；而"宁可明确地宽一点，也不要让明明贴着的被判成没接"。

### 根因② 覆盖计数按「边的种类」，而不是按「到没到」

v1079 起主管与支管**同列定线**（实体中心线重合，只有显示副本错开）。此时最短路会沿主管直接走到支管端点——拓扑完全等价，但**路线里一条 `branch:` 边都没有**。

旧判定：

```js
if (r.branch.some(s => s.key.indexOf('branch:') === 0)) covered[r.zi]++;
```

⇒ 覆盖恒为 0。而实际上 `成路 24 条/目标 24`，全部建出来了。

**修复（v1084d / v1084e）**：改为**按目标点数**——每区两个目标（支管两端），到达一个计 1，满 2 闭合。目标本身就是 `branch-start/branch-end` 两个切口，到达即代表该端进水；也不再依赖「主支管是否重合」这种与水流无关的布局细节。

### 根因③（v1084e 收口）同一个口径写了三份，第三份在诊断里

v1084d 只改了 `start()` 和 `routesAll()`，`whyNot()` 里还留着旧口径 ⇒ **控制台报「12 区 0/2」，点下去却能演示**。
排查工具自己撒谎，比没有工具更糟——用户会拿着错数字去改一张本来没问题的图。

**修复**：抽出纯函数 `coverageOf(routes,total)`，`start()` / `routesAll()` / `whyNot()` 三处共用；`whyNot()` 的 pass 判定与 `start()` 的四道条件（`wholeFieldClosed && routes.length && !incomplete && activeCount`）逐一对齐。

## 3. 为什么这次拖了 4 轮才查出来

不是技术难，是**可观测性**和**归因方向**错了。

1. **5 个裸 `return`**。判定链上每一道门不通过就直接 `return`，一句原因都不记。表现就是「什么都没发生」——没有任何线索指向是在第几步断的。
   → 规矩：判定链上每次拒绝都必须 `diag.zones.push({zi,reason})` 或至少 `diag.missing++`。

2. **同一件事两套判据**。`validateConnection.strictNodeEntry` 判「总管折点顶点」，`buildFlowRoutes` 的 coupler 判「顶点 + 节点到主管 ≤0.5 m」——任一不过就静默丢弃。质检说通、建图说不通，用户看到的就是「预览显示接上了，演示说没接」。
   → 规矩：一个物理事实只留一份判据，抽纯函数，两个调用方共用。

3. **文案把程序偏差归因到用户操作**。原提示是「请把总管画到紫色主管节点处」——而实际偏差是程序内部 0.96 m。用户照着改了 4 轮图，越改越乱，最后说「完了，彻底乱套了，我都没信心修复好了」。
   → 规矩：提示里必须带**实测米数**，让用户能自己判断是"我没画到"还是"程序算错了"。

4. **回滚不是排查手段**。v1053、v1030 上同样报错——因为根因在 v1079（同列定线）和 v1082（双世界），回滚到这两个版本之后仍然包含它们。三次回滚、两次换版本，全部无效。
   → 规矩：**先定位门禁，再决定要不要回滚**。回滚只能解决"新版本引入的回归"，解决不了"老版本就存在的设计缺陷"。

5. **版本徽标只显示数字段**。`index.html` 的 `#ryNavVersion` 用 `/^v?(\d+)/` 截断，`v1084-coverage` 永远显示成 `v1084`。用户据此判断"没更新"，实际上已经更新了。
   → 确认线上版本只能看这三处：悬停徽标读 `title`、控制台 `document.getElementById('ryNavVersion').dataset.ryVersionFull`、或直接 curl `sw.js` 搜 `const VERSION`。

## 4. 标准排查流程（下次照做）

```
① 拿一行数字
   控制台 RyMapFlowDemo.whyNotText(0)
   ↓
② 门禁在哪？（collect / validation / routes / pass）
   ↓
③ 是 validation 的 node-not-connected？
   → 读【数据】里「最近节点离主管 x m / 离总管 y m」
   → x ≤ LOOSE_ATTACH_M(3) 仍报错  ⇒ 容差或世界换算问题（根因①类）
   → x 明显大于 3          ⇒ 用户确实没画到，属正常拒绝
   ↓
④ 是 routes 门禁（图建了但覆盖不全）？
   → coverage.counted 与「成路 N 条」对不上 ⇒ 口径分叉（根因②③类）
   → counted 对得上但 missingZones 非空 ⇒ 真的断链，看 diag.zones[].reason
   ↓
⑤ 在 Node 里造同构合成数据复现（模板见 tests/v1084c_demo_connect.test.cjs）
   —— 用户截图里的每个数字都当断言：成路 24 条 / 节点 0/3 / 阀离支管 0.96m
   ↓
⑥ 修完加锁：把这些数字写成测试断言，注释里写清"用户实测原话"
   ↓
⑦ 全量测试 + 与基线 diff（必须用 git worktree 实跑基线，见第 6 节反模式）
```

## 6. 反模式（这几件别再干）

- ❌ **靠"退一个版本试一次"**。先拿门禁名和数字，再决定要不要回滚。
- ❌ **在判定链上留裸 `return`**。要么记账，要么别拒绝。
- ❌ **同一个物理事实写两处判定**。抽纯函数；`coverageOf()` 就是这么来的。
- ❌ **把程序内部偏差写成"请用户检查/重画"**。提示里必须有实测米数。
- ❌ **`git stash push -- <untracked>` 造基线**。它会对未跟踪文件静默失败（"No stash entries found"），得到的是假基线。用 `git worktree add <tmp> <sha>` 实跑。
- ❌ **看版本徽标数字判断是否更新**。徽标只显示数字段，后缀被截断。
- ❌ **相信"回滚就好"的直觉**。设计缺陷跟着代码走，不跟着版本号走。

## 附录：先分清「坏了」和「被总闸关了」

2026-11-14 排查「段总管到底还参不参与计算」时，我自己踩了一次，值得留档。

### 现场

`mod/inline-09.js` 的 `tlPushToHydraulicCalc()`（三级方案 → 水力计算器自动推送）第一行：

```js
if (!d || !d.frontPipe) return false;   // v1015 起 frontPipe 恒 null ⇒ 恒 false
```

看起来是个明确 bug。**但修它没用** —— 因为 `hydraulic-calc.js` 里还有一道更上游的门：

```js
importThreeLevel: function (data) {
  if (window.RY_HC_RESERVED) return null;   // ← 真正的阻断点
```

而 `mod/inline-23.js` 全文就是一行：

```js
window.RY_HC_RESERVED=true;
```

依据 v135（2026-09-23 用户指令）：「水力计算器」内容暂不展示，只保留导航入口。
`mount / setConfig / importThreeLevel` 三入口全被它守卫，**整块功能是刻意停用的**。

那行 `!d.frontPipe` 是 v1015 遗留的**够不到的死门禁**，不是当前故障点。

### 规矩

1. **看到"函数恒返回 false / 点了没反应"，先往上找一层总闸**，别在最内层改。
   本项目已知总闸：`RY_HC_RESERVED`（水力计算器整块）、`ppPipeLayerSuppressed`（管路可见层）、`__ryPipelineLayerVisible`（管路显隐开关）。
2. **总闸关着的代码路径不许"修"**。改了跑不到、也无法验证，属**假修复**——比不改更坏，因为它会让人以为"这块已经好了"。
3. 正确动作只有两个：**加标注**（写清"为什么这里是死的、启用时要先改哪里"），或**等总闸打开时一起改**。
4. 判断"这个变量/函数还有没有用"，必须查**消费链**而不是看它是否出现在画面上。
   例：段总管 `segTrunk` 图面不画（`if(false && ...)`），但仍是 `segWorstPath` 的路径来源、`tlFrontLenUse` 的长度兜底、`segLL` 的干线——v900 误删过一次，扬程链死了两个版本才被 v1017 恢复。
